## 整改范围

- 统一账号、旧密码登录接口、Django admin 共用失败锁定及安全审计。
- 记录登录成功、失败、锁定、密码修改及 Directus 写操作；管理日志补齐来源 IP、User-Agent、request ID，不记录密码、验证码、Cookie 或请求正文。
- 拒绝历史 DRF Token 请求头认证，仅接受 LoginSession。用户可能需要重新登录。
- LoginSession 默认三十分钟无已认证 HTTP 请求失效，绝对有效期仍为三十天；Django 账号及 admin 会话也采用三十分钟滑动过期。HTTP 轮询会刷新闲置时间，因此这不是键盘鼠标无操作检测。
- WebSocket 心跳不刷新会话，收到消息及等待消息时重新验证会话，闲置连接最多约六十秒发现过期/撤销；增加 Origin 验证。
- API、安全日志用 WatchedFileHandler，由主机 logrotate 按日轮转，保留两百份，不按大小提前覆盖。老的 `.1` 等轮转文件保留并纳入备份。上线当日不足六个月历史，不能生成缺失的历史记录。
- 数据库备份使用私有目录和 0600 文件，先写临时文件、校验 gzip，再发布正式备份并计算 SHA256；失败返回非零，清理半成品。
- Compose 后端端口仅监听本机，Redis 密码必填，健康检查使用密码；日志目录挂载到主机。当前生产使用 systemd，不会因修改 Compose 自动改变。

## 上线与回滚

1. 从生产提交建立独立安全修复分支，只发布本次文件，保留生产的学习实验、定时提醒及其他功能配置。禁止将主工作区全部未提交修改上线。
2. 记录生产当前提交、服务配置与定时器；上线前用权限 0700 的专用目录备份环境、服务配置、日志轮转配置和数据库。不要输出环境内容。
3. 通过 Git 发布修复，在生产 `git pull --ff-only` 指定分支；先运行 `manage.py migrate`，再重启 Daphne 和 Celery。迁移 `0078` 给已有会话初始化最后访问时间，不改用户密码。
4. 当前主机路径为 `/opt/unimind`，服务身份为 root/www-data；安装 `deploy/logrotate/unimind` 到 `/etc/logrotate.d/unimind`，权限 0644。若服务身份变化必须同步更新 `create` 和 `su`。运行 `logrotate --debug /etc/logrotate.d/unimind`，确认 logrotate.timer 正常。应用进程能够写本地日志，因此还需独立副本/访问审计，不能把轮转当防篡改。
5. 安装 `scripts/unimind-backup.service`、`.timer` 到 systemd；daemon-reload 后先手动启动 service，确认退出码、备份内容及权限，再启用 timer。每日 03:00 左右执行，保留三十天数据库备份。不要同时保留重复 cron。
6. `manage.py check --deploy`、loopback health 数据库/缓存正常、匿名 me 返回 401、HTTPS 响应头、登录/管理写操作的审计记录均需检查。不要用真实用户试错锁定。
7. 代码故障时停止服务，切回记录的旧提交并重启；新增 last_seen_at 列可保留，旧代码不依赖它，不需要删列或恢复数据库。日志/备份配置按上线前副本回滚。

## 备份、恢复与告警

本地数据库脚本为 `scripts/backup_db.sh`。OSS 原始对象仍需单独核验版本控制和备份；本机归档不包含云上对象及单独学习沙盒的全部状态。

用户选择现有生产机。本次本机文件备份另包含媒体、日志、环境文件、已配置的账号 RSA 与 DSH 会话目录，保留七天；数据库保留三十天。文件备份在 root 私有目录中保存，不代表磁盘加密或异地容灾。异地仓库与独立审计副本仍待建设。

每季度和重大升级后在隔离环境恢复一次，并记录时间与结果：

1. 选择一次备份及其 SHA256，执行 `shasum -a 256 -c 文件名.sql.gz.sha256` 和 `gzip -t 文件名.sql.gz`。
2. 在独立 PostgreSQL 实例创建空库，用 `set -o pipefail` 后 `gzip -dc 文件名.sql.gz | psql -v ON_ERROR_STOP=1 -d 独立测试库` 恢复；禁止指向生产库。
3. 文件归档先验证 SHA256，运行 `tar -tzf files_时间戳.tar.gz` 核对目录，再解压到隔离目录核查媒体、日志、RSA 和配置；禁止直接覆盖生产路径。
4. 核对课程、用户、学习记录、媒体访问和账号登录；记录备份时间、恢复开始/结束、可恢复时间点、数据量、错误及执行人。RPO/RTO 以实际演练为准。

每日核查备份服务失败状态、最新成功备份年龄、磁盘容量、服务存活和安全事件。监控建议条件：最近成功备份超过二十六小时，备份服务失败，磁盘超过 85% 或剩余低于 10 GB，日志轮转失败，异常登录/权限变更。通知接收人及实际通道待运营单位配置，本轮不向外部发送消息。

## 管理制度草案

运营单位需填写并批准：安全负责人、运维负责人、审计复核人、应急联系人。人员可按组织实际承担职责，但变更申请人、复核人与审批记录需可追溯，不以两个超级管理员代替管理制度。

- 资产与边界：登记域名、服务器、数据库、Redis、OSS、Directus、DSH、外部 AI/ASR 服务及数据流；确定定级对象、责任主体、数据类别、备份范围及供应商责任。ICP备案不等同于等保备案。
- 账号与人员：实名独立账号，按需授权；离职/停用及时撤销会话和密钥；季度复核权限。禁止共享 root 日常运维。生产操作使用受控入口并保留记录。
- 变更与漏洞：变更前备份、评估影响、记录回滚；发布经过代码审查及必要冒烟。定期核查依赖与主机漏洞，记录处置、延期理由和复核结果。代码中的上传格式检查不能替代主机恶意代码防护。
- 审计：每日查看锁定及异常事件；定期核查日志时间、覆盖范围、留存、访问及备份；不采集密码或验证码。数据库审计记录及独立日志副本共同核验。
- 应急：发现入侵或泄露后记录时间、资产及影响，保存证据；隔离受影响入口，撤销凭证；恢复服务前修补并检查；安全负责人按事件情况核定通知和报告义务；复盘记录原因、处置与改进。不得先删除日志或覆盖受损环境。
- 供应商与数据：记录 AI/ASR 服务接收哪些数据、存储位置、用途及删除安排；核验云服务安全责任、主机与恶意代码防护、物理环境证明。
- 定级备案与测评：补齐业务影响分析、资产清单、网络拓扑、责任人、制度批准、培训、运维记录、恢复演练、整改证据及正式备案/测评材料。尚未取得的材料统一标记待提供。
